# 三插件批量下载实现分析

## 结论

三个扩展的核心都是同一种结构：

1. `content/index.js` 在平台页面注入下载按钮和批量选择界面。
2. content script 通过 `chrome.runtime.sendMessage` 把任务交给 `js/background.js`。
3. background service worker 再用 `chrome.scripting.executeScript({ world: "MAIN" })` 进入网页主世界，读取页面状态、Cookie 和站点自己的签名函数。
4. 先生成候选列表，用 Tabulator 让用户筛选，再逐条调用详情接口取得真实媒体 URL。
5. 三者都以串行队列为主，任务之间有等待，没有无限并发。

因此，不能只把几个下载 URL 解析函数抽出来就变成纯 HTTP 工具。最稳妥的独立工具应保留一个内嵌 WebView2 登录/签名环境，但把任务管理、文件下载和音视频合并移到本地程序。

## 共用实现

- 三个扩展的 `author` 都是 `videohelper`，并复用了相同的 Tabulator、文件大小计算、ZIP/附件导出、分段 fetch 和进度回传框架。
- 下载有两条路径：
  - 直接调用 `chrome.downloads.download({ url, filename })`。
  - 用 `fetch` + `Range` 逐段读入 Blob，支持暂停/继传和进度，再通过扩展页下载。
- 任务数据在 content script、background 和页面主世界之间传递；部分大 Blob 通过 IndexedDB/临时扩展页中转。
- “收集”不等于“下载视频”：另一条路径会将正文、图片、评论和元数据打包成 ZIP/Markdown，并可导入小书匠。三合一工具的首版可先不做这块。

## 抖音：阿抖 1.5.6

### 列表获取

- 作者作品：`/aweme/v1/web/aweme/post/`，参数包含 `sec_user_id`、`max_cursor`、`count: 40`。
- 合集：`https://www-hj.douyin.com/aweme/v1/web/mix/aweme`，参数包含 `mix_id`、`count: 15`。
- 通过 `has_more` + `max_cursor` 递归翻页，每页等待约 1 秒，单次请求失败最多重试约 5 次。
- 发布包描述中写有“播放记录/我喜欢的视频”，但在当前版本可定位的批量列表代码中，明确实现的是作者作品和合集；前两项需要后续真机页面验证。

### 单条解析和下载

- 详情：`/aweme/v1/web/aweme/detail`，传入 `aweme_id`，请求使用 `credentials: "include"`。
- 视频地址优先取 `play_addr_h264`，其次 `play_addr_265`，再回退到 `play_addr`；音频来自 `music.play_url`。
- 评论：`/aweme/v1/web/comment/list/`，子评论：`/aweme/v1/web/comment/list/reply/`，都使用登录 Cookie。
- 用 `declarativeNetRequest` 将 `douyinvod.com` 请求的 `Referer` 改为 `https://www.douyin.com/`，否则部分 CDN 链接无法直接下载。
- 批量选中后以 `for` 循环逐条解析/下载，条目之间等待约 2 秒。

### 脱离扩展的要点

- 需要保留抖音登录 Cookie、User-Agent 和 `Referer`。
- 媒体 URL 有时效，不应长时间持久化；应在真正开始下载前临时解析。

## B站：爱哔哔 0.4.1

### 列表获取

- 作者作品总数：`/x/space/navnum?mid=...`。
- 作者/媒体列表：`/x/v2/medialist/resource/list`，每页 `ps: 20`，先后以两个 `direction` 获取当前稿件两侧的列表，再用 `oid` 翻页。
- 番剧集数：`/pgc/view/web/ep/list?season_id=...`。
- 普通投稿的分 P 列表、合集和番剧都被归一化为 `downloadId + title + link` 任务。

### 清晰度解析与合并

- 普通视频：`/x/player/playurl` 和 `/x/player/wbi/playurl`，参数包含 `bvid`、`cid`、`qn: 120`、`fnval: 4048`、`fourk: 1`。
- 番剧：`/pgc/player/web/playurl` 和 `/pgc/player/web/v2/playurl`。
- 兼容两种结果：
  - `durl`：通常是已封装的单文件。
  - `dash`：视频和音频分离，按画质 ID 选视频流，再匹配音频流。
- 扩展会对 `base_url` 和 `backup_url` 做 OPTIONS/大小探测，选择可用 CDN 地址。
- 内置约 30 MB 的 `ffmpeg-core.wasm`，用于在网页内合并 DASH 音视频。
- content script 使用 `2147483648` 字节（2 GiB）作为大文件界限。超出浏览器能力时，通过 `showDirectoryPicker` 分别写入音频和视频，并附带手动合并说明。
- 弹幕另调 `/x/v2/dm/web/view` 和 `/x/v2/dm/web/seg.so`，可生成 ASS/XML/JSON。

### 批量队列

- 合集/作者列表可在弹窗 `links.html` 中筛选清晰度和“音视频分离”选项。
- content script 维护 `sequeneIds`，每次只触发一个任务。background 下载/合并完成后会点击隐藏的 finish handle，再开始下一条，属于严格串行。

### 脱离扩展的要点

- 独立程序应直接调本地 `ffmpeg.exe`，不应继续使用 ffmpeg.wasm；性能、大文件和内存占用都会明显改善。
- 需从 WebView2 会话中取得 Cookie，否则高清流、大会员清晰度和番剧权限会与网页登录状态不一致。

## 小红书：小草莓 2.3.3

### 列表获取

- 批量页面不是直接调一个简单列表 API，而是每秒向下滚动一屏，直到 `scrollTop` 不再变化，然后读取页面的 `window.__INITIAL_STATE__`。
- 作者页从 `user.notes._rawValue` 取数据，根据 URL 的 `tab` 在 `note / fav / liked` 中选择。
- 收藏夹页从 `board.boardFeedsMap._rawValue[boardId].notes` 取数据。
- 列表条目保留 `noteId`、类型、标题、作者和 `xsecToken`。

### 签名、详情和下载

- 优先从 `window.__INITIAL_STATE__.note.noteDetailMap` 或页面内存缓存取详情。
- 缓存没有时，POST `/api/sns/web/v1/feed`，请求体包含 `source_note_id`、`xsec_source`和 `xsec_token`。
- 该请求不能只复制 URL：扩展直接调页面里的 `window._webmsxyw(...)` 产生 `x-s` / `x-t`，并结合 Cookie、localStorage 和页面的 MNS token 组装 `x-s-common`。
- 评论：`/api/sns/web/v2/comment/page`，子评论：`/api/sns/web/v2/comment/sub/page`，都带 `xsec_token` 和动态签名头。
- 无水印原视频可通过 `video.consumer.originVideoKey` 组合 `https://sns-video-hw.xhscdn.com/{key}`。
- 某些页面无法直接取状态时，扩展会创建 offscreen document，fetch 页面 HTML，从 `<script>` 中解析 `window.__INITIAL_STATE__`。
- 批量下载也是串行 `for` 循环，条目之间等待约 2 秒。

### 脱离扩展的要点

- 这是三个平台里对真实网页环境依赖最强的一个。纯 `HttpClient` 重写动态签名会很脆弱，不建议作为首版方案。
- 签名和 feed/评论请求应保留在 WebView2 页面主世界内执行，只把归一化后的任务和媒体 URL 返回给本地层。

## 发布包边界

- 当前拿到的是 Edge 安装目录中的发布产物，不是未压缩的原始开发仓库。
- 三份主要 `background.js` 均已被 Webpack 打包和变量压缩，目录中没有 source map、`package.json` 或完整许可证文件。
- 可以把接口流程、数据模型和队列策略作为重写参考；如果要直接复用或发布其代码，需先确认作者授权和对应站点条款。

## 三合一桌面工具建议

### 推荐技术路线

首版建议使用 **.NET 8 + WPF + WebView2 + 本地 ffmpeg**：

- WebView2 使用工具自己的持久化 User Data 目录，分别登录三个平台。
- 每个平台一个 adapter：`DouyinAdapter`、`BilibiliAdapter`、`XiaohongshuAdapter`。
- 列表和详情解析 JS 在 WebView2 主页上下文内执行，返回统一的 `MediaTask` JSON。
- C# 层负责任务队列、断点续传、失败重试、限速、文件命名、去重和进度。
- B站 DASH 任务下载完后调本地 `ffmpeg.exe -c copy` 合并，避免整个媒体进入内存。
- 默认并发数建议为 1，稳定后再对不同平台独立提高到 2–3；请求列表和详情仍保留间隔。

Electron 能更快复用现有 JS，但体积和内存占用更大；Tauri 体积更小，但首版需要更多 Rust/JS 桥接工作。对当前 Windows 单机工具，WPF + WebView2 是体积、开发速度和网页兼容性之间更平衡的选择。

### 统一任务模型

```text
MediaTask
  platform        douyin | bilibili | xiaohongshu
  itemId          aweme_id | bvid+cid/ep_id | noteId
  title
  author
  sourceUrl
  mediaKind       video | image | audio
  streams[]       url, quality, codec, size, headers
  mergeRequired   true/false
  authContext     WebView profile reference, not raw cookies on disk
  outputPath
  status/progress/error
```

### 建议的 MVP 顺序

1. 单条 URL 解析 + 下载，先支持抖音和小红书单视频、B站单 P。
2. B站 DASH 音视频合并。
3. 作者/合集/收藏夹列表获取和可勾选任务表。
4. 串行批量队列、断点续传、去重和失败重试。
5. 弹幕、评论、Markdown/ZIP 等增强功能。

## 本轮验证边界

以上结论来自对三个已安装发布包的静态调用链、接口字符串和下载队列代码分析。本轮没有点击实际下载，也没有对三个平台做网络抓包，因此属于静态确认，不是当前站点的端到端可用性验收。
